# Recommended Paper Architecture for a Ten-Layer Code Knowledge Graph Repair System

## What the five papers really establish

Across the five papers, the shared lesson is not simply that “graphs help software repair.” The stronger pattern is that repository-level repair depends on four coupled design choices: how the repository is represented, how that representation is exposed as queryable evidence, whether there is an explicit reasoning stage between localization and editing, and how candidate patches are verified and ranked. SGAgent operationalizes this with a locate–suggest–fix workflow and a knowledge-graph toolkit; ARISE does it with a statement-level program graph and a three-tier API; LIDL does it with LLM-aware semantic annotations plus counterfactual validation; Prometheus does it with a multilingual unified graph plus issue classification and reproduction; and KGCompass does it with issue/PR-aware candidate ranking, path-guided patch prompting, and test-based reranking. citeturn9view0turn11view0turn13view0turn17view0turn19view1turn20view0turn22view0turn22view3

Two version caveats matter before you write your related-work section. First, KGCompass has materially different reported numbers across versions: the v1 HTML/body widely discussed in 2025 reports 45.67% repair and 51.33% function-level localization, while the later arXiv v3 abstract reports stronger single-repair-model results of 58.3% repair and 56.0% function localization. Second, the paper listed as *Prometheus: Unified Knowledge Graphs for Issue Resolution in Multilingual Codebases* is the v1 paper under arXiv 2507.19942, but a later v2 HTML page under the same identifier reframes Prometheus around memory-enhanced long-horizon navigation and reports Verified / SWE-PolyBench results. ## The research gap your paper can credibly own

Your strongest claim should **not** be “knowledge graphs improve repair,” because these five papers already establish that. Your stronger and more defensible claim is: **current graph-enhanced repair systems cover different slices of software reality, but none of this five-paper set presents a single, layer-aware, queryable software representation that spans from low-level code form to socio-technical evolution**. SGAgent remains centered on structural entities and a repair-oriented toolkit; ARISE extends downward to statements and def-use flow; LIDL broadens outward to prompts, config, tools, and memory artifacts; Prometheus keeps a deliberately minimal file/AST/text schema for multilingual portability; KGCompass adds issue/PR history and multi-hop path evidence. Those are important advances, but they are still partial views of the software system. citeturn9view1turn14view0turn16view1turn17view0turn19view0turn19view1turn22view1

That is why your ten-layer CKG is promising. It can be framed not as “a bigger graph,” but as **a complete software evidence substrate**. I would present the ten layers as four broader bands so reviewers can immediately understand what is new: code form and names (Layers 1–3), execution semantics (Layers 4–7), assurance and business meaning (Layers 8–9), and temporal/social context (Layer 10). This grouping makes your contribution legible because it unifies the lower-layer focus of SGAgent and Prometheus, the flow/state emphasis of ARISE, the semantic artifact typing of LIDL, and the repository-history emphasis of KGCompass. It also reveals your main differentiation: runtime/production, test/verification, domain/business, and socio-technical evolution are only partially addressed in these papers, typically as workflow aids rather than as explicit graph layers. citeturn9view1turn14view0turn16view1turn17view0turn19view0turn20view0turn22view1

The second half of your gap is **queryability**. ARISE separates the graph from the tool API and shows that first-class structured slices matter. SGAgent builds a scenario-oriented toolkit on top of its KG. Prometheus wraps graph access in a retrieve–select–refine context agent. LIDL retrieves by semantic annotations and validates over minimal subgraphs. KGCompass packages entity paths into prompts and still treats patch ranking as a formal system component. So your paper should treat the **query layer** as a contribution equal in status to the graph schema itself. If you bury queries under the agent section, you will understate one of the central ideas that the literature has already shown to be important. citeturn14view0turn11view0turn19view1turn17view0turn22view2

In other words, the cleanest thesis for your paper is this: **repository-level issue solving is limited by incomplete software representations exposed to the agent; a ten-layer CKG and a layer-aware query interface expose the missing evidence needed for codebase understanding, localization, repair planning, and verification**. That thesis is more differentiated than “our agent is better,” and it matches the actual frontier these five papers are collectively moving toward. citeturn13view0turn11view0turn17view0turn20view0turn22view1

## The architecture I recommend for your system

I would architect the system as **two planes**. The first is an **offline repository-to-CKG plane** that ingests code and non-code artifacts into the ten-layer graph, normalizes them, and builds query indexes. The second is an **online issue-to-patch plane** that plans what to query, localizes candidates, expands them into repair hypotheses, generates patches, and validates the results. This split is strongly supported by the literature: ARISE is the clearest example of separating graph construction, tool API, and agent loop; SGAgent shows that a planning stage between localization and fixing matters; Prometheus and KGCompass show that reproduction and patch verification belong inside the architecture; and LIDL shows that a validator operating over minimal context can materially improve ranking. citeturn13view0turn14view0turn11view0turn9view4turn17view0turn20view0turn22view3

The paper will read most cleanly if the architecture looks like this:

| Recommended component | What it should do | Why it belongs in the paper |
|---|---|---|
| **Repository-to-CKG ingestion** | Parse source code, docs, configs, tests, issues, PRs, commits, authors, and optional runtime artifacts into a ten-layer graph. | This is your core representation contribution. |
| **Layer-aware query service** | Expose the graph through structured operators: lookup, traversal, slicing, path search, temporal/history joins, evidence packaging. | This is your second core contribution. |
| **Issue triage and query planner** | Read the issue, classify failure type, decide which layer bundles to inspect first, and produce a retrieval plan. | This is how you convert “ten layers” into operational behavior. |
| **Graph navigator and localizer** | Narrow the search space to candidate files/functions/statements/tests/components using layer-specific queries. | This is where the CKG should beat a graph-free agent. |
| **Repair planner** | Convert retrieved evidence into root-cause hypotheses and repair constraints before editing. | This is the SGAgent-style insight you should inherit. |
| **Patch generator** | Produce candidate diffs grounded in structured evidence packages. | This proves the graph is useful downstream, not only for retrieval. |
| **Verifier and ranker** | Use regression tests, reproduction tests, and evidence-aware ranking to choose the final patch. | This is a must-have, not an appendix detail. |
| **Trajectory memory / evidence cache** | Store retrieved graph evidence and failed attempts so the agent does not repeatedly traverse the same regions. | This supports long-horizon codebase understanding and keeps the loop stable. |

If you want the architecture to look novel rather than busy, keep the online loop to **four operational roles** even if multiple prompts exist behind the scenes: a triage/planning role, a navigator/localizer role, a repair-planning role, and a repair/verification role. That is enough to preserve SGAgent’s “suggestion” insight without turning the paper into agent choreography, and it keeps the visual and conceptual center of gravity on the CKG plus the query layer. ARISE is especially instructive here because its main contribution is the graph/tool layer injected into an otherwise fixed SWE-agent loop, which is exactly the kind of isolation reviewers tend to trust. citeturn11view0turn9view4turn14view0turn13view4

Your query interface should be a **formal contribution**, not a bag of tools. A clean framing is to define four operator families. The first is **entity lookup** queries: files, symbols, tests, issues, PRs, services, owners, and business entities. The second is **neighborhood and path** queries: call/import containment, control-flow, dependency, test-to-code, issue-to-code, commit-to-code, and owner/churn relations. The third is **semantic slice** queries: control/data-flow slices, state propagation, runtime-to-static joins, and failing-assertion backtracking. The fourth is **evidence-packaging** queries: bundle the best cross-layer evidence under a token budget, with explicit provenance. That structure synthesizes SGAgent’s toolkit, ARISE’s three-tier API, Prometheus’s retrieve–select–refine retrieval loop, LIDL’s annotation-driven retrieval, and KGCompass’s path-guided evidence packaging. citeturn11view0turn14view0turn19view1turn19view2turn17view0turn22view2

One feature I would emphasize strongly is a **layer-aware query planner**. This is the natural place where your ten-layer graph becomes more than a static index. Stack-trace-heavy issues should route toward structure, flow, and test layers first. Prompt/configuration or behavior mismatches should route toward semantic, runtime, and domain layers. Historical regressions should route toward tests and evolution history. LIDL’s symptom-to-annotation reasoning, Prometheus’s issue classification, SGAgent’s suggestion stage, and KGCompass’s path mining all imply the same principle: the agent should decide not only *what* to query, but *what kind of evidence* to query first. citeturn17view0turn20view0turn11view0turn22view1

## The paper outline I recommend

For writing structure, the closest templates are ARISE for a crisp separation of graph, API, and agent loop; SGAgent for staged reasoning and ablations; KGCompass for a motivating example plus candidate-coverage analysis; LIDL for component-level analyzer/validator analysis; and Prometheus for putting issue reproduction and verification inside the main method rather than treating them as invisible infrastructure. The outline below merges those strengths into a form that matches your contribution better than any single prior paper. citeturn8view0turn12view0turn22view0turn16view0turn20view0

| Recommended paper section | What this section must accomplish | Must-have content |
|---|---|---|
| **Introduction** | State the real problem and the missing evidence in current repair systems. | Frame repository issue solving as an evidence problem, not just an LLM prompting problem. Introduce the ten-layer CKG, query layer, and Agent+CKG system. |
| **Motivating example** | Make the need for cross-layer evidence concrete. | Show one issue where file-level search is insufficient and the correct explanation requires multiple layers or multi-hop evidence. |
| **Problem formulation and research questions** | Define the task formally and delimit the scope. | Formalize repository-to-CKG construction, issue-to-patch repair, and layer-aware retrieval. State the RQs clearly. |
| **Comprehensive CKG construction** | Present the graph as a reusable software representation. | Define nodes, edges, attributes, layer semantics, cross-layer links, storage model, ingestion algorithms, and optional artifacts for runtime/domain/evolution layers. |
| **Layer-aware query methods** | Show how the graph becomes actionable. | Define query families, structured outputs, evidence provenance, query routing, context packaging, and complexity/latency considerations. |
| **Agentic issue-resolution system** | Demonstrate how the CKG is used downstream. | Describe the online loop: issue triage, localization, repair planning, patch generation, verification, ranking, and memory. Make clear what is fixed across baselines. |
| **Experimental setup** | Make the evaluation look rigorous and fair. | Benchmarks, models, baselines, action spaces, token budgets, prompt parity, and evaluation harness. |
| **Results** | Separate representation quality from end-to-end repair quality. | CKG stats, query metrics, localization metrics, repair metrics, cost, latency, ablations, and case studies. |
| **Related work** | Position against graph systems, agent systems, and defect-localization systems. | Organize by design axis: graph scope, tool API, staged reasoning, validation, heterogeneous artifacts, multilingual support. |
| **Limitations and threats** | Preempt reviewer objections. | Benchmark bias, incomplete runtime signals, optional population of upper layers, graph staleness, and generalization beyond Python/Verified. |
| **Conclusion** | Reinforce the reusable systems contribution. | End with “ten-layer CKG + query layer enables better issue solving,” not just “our agent scores X%.” |

The single most important structural choice is to give the **CKG section** and the **query section** separate identities before you describe the agent. If you merge graph construction, query methods, and agent workflow into one giant “method” block, the graph will look like an implementation detail of the agent rather than a reusable substrate. ARISE avoids that by isolating graph, tool API, and loop; SGAgent similarly separates KG construction, toolkit implementation, and multi-agent framework. Your paper should do the same because your graph is the substrate and your agent is the downstream proof of utility. citeturn8view0turn13view0turn14view0

In the Introduction, I would also resist the generic opening that “LLMs struggle with large codebases.” That statement is true but too weak. The stronger opening, and the one more faithful to the five papers, is that **repository issue resolution requires evidence spanning static code, execution clues, tests, documentation, and change history, but current graph-enhanced agents expose only subsets of that evidence**. That is the framing that naturally justifies your ten-layer design. citeturn9view1turn14view0turn16view1turn19view0turn22view1

## The evaluation and ablation plan that will convince reviewers

The evaluation should prove **three different propositions** rather than one blended claim. First, the ten-layer CKG is a better repository representation. Second, the query interface exposes that representation effectively to an agent. Third, the agent converts better evidence into better repairs. ARISE gives you the best methodological precedent here because it holds the scaffold, prompt structure, turn count, and budget fixed while varying only the available graph tools, which makes its causal claim about the tool layer much cleaner. SGAgent, LIDL, and KGCompass then show how well-designed component removals reveal which stages are actually load-bearing. citeturn12view4turn13view4turn9view4turn16view5turn21view0

For the main benchmark, SWE-bench Verified is the right primary target because it is a human-validated subset of 500 instances specifically intended for more reliable evaluation of coding agents. Your most important internal comparison should be **Agent Only vs Agent + CKG** under the **same** base model, **same** verifier, **same** patch budget, and **same** action space. That is the causal comparison reviewers will trust. By contrast, mini-SWE-agent should be treated as an **external scaffold baseline**, not as your main causal ablation. The official Verified site uses mini-SWE-agent as the standardized bash-only setup for apples-to-apples language-model comparison and explicitly warns that version 1.x and 2.x results are not directly comparable because the protocol changed. The mini-SWE-agent repository itself also frames the system as a deliberately minimal bash-only baseline with a linear history and independent `subprocess.run` actions. citeturn31view1turn31view0

If you evaluate only on SWE-bench Verified, avoid a multilingual repair claim. The original SWE-bench family is built from Python repositories, and Prometheus had to add a separate multilingual benchmark precisely to justify multilingual claims. So if your ingestion pipeline is language-agnostic, claim **representation generality** at the graph level, but keep **repair generalization** scoped to what you actually evaluate. citeturn30search3turn18view3

A convincing metric package would look like this:

| Metric block | Recommended measures | Why each block matters |
|---|---|---|
| **End-to-end repair** | % Resolved / Pass@1, average cost, average time per issue | This is the outcome measure everyone will compare first. |
| **Localization quality** | File / function / line Recall@k, MRR, IoU | This lets you show where the CKG improves understanding before patching. |
| **Query efficiency** | Token usage, number of tool/query calls, latency, context-bundle coverage, average path length | This proves your graph is not merely accurate but operationally efficient. |
| **CKG construction quality** | Build time, node/edge counts by layer, ingestion failure rate, storage size, cross-layer link density | This proves the representation itself is feasible and complete enough to matter. |
| **Graph usefulness analysis** | Candidate-set coverage, unique fixes, layer usage rate, ablation drops by layer group | This is where you show *which* layers and queries actually matter. |
| **Qualitative analysis** | Case studies and failure taxonomy | This is where the ten-layer story becomes visible to readers. |

This metric set is directly aligned with the literature. SGAgent reports resolved rate, localization accuracy, and cost. ARISE adds file/function/line localization, Coverage@budget, and repair–localization correlation. KGCompass reports candidate coverage, hop distribution, and patch-ranking upper bounds. Prometheus reports graph statistics and monetary cost. LIDL reports Top-k, MAP, MRR, tokens, and component-level ablations. Your paper should feel similarly multi-perspective rather than relying on one leaderboard number. citeturn9view4turn13view4turn21view4turn21view0turn18view3turn18view5turn17view0

The best ablations for your system are the ones most clearly motivated by these five papers. Remove the **planning/suggestion** stage to test the SGAgent-style claim that planning improves repair more than localization. Remove **flow/state layers** or their slice queries to test the ARISE-style claim that finer execution evidence improves function- and line-level localization. Remove **upper-layer annotations or validator-style ranking** to test the LIDL-style claim that higher-level semantic evidence matters. Remove **issue/PR/evolution edges** to test the KGCompass-style claim that multi-hop historical context reduces the search space. Remove **reproduction-test reranking** to test the verification claim shared by KGCompass, SGAgent, and Prometheus. And borrow one more ARISE lesson: compare **structured query outputs** against natural-language tool summaries. ARISE showed that the latter may add cost without adding value. citeturn9view4turn12view5turn16view5turn21view4turn21view0turn20view0

Do not stop at aggregate metrics. Add at least **three case studies**, each chosen to activate different layer bands: one issue solved mostly by lower-layer static evidence, one requiring test/runtime or configuration evidence, and one requiring issue history or socio-technical context. KGCompass’s motivating example, LIDL’s running example, and SGAgent’s suggester case study all show that qualitative examples are where readers most clearly see why an architecture is necessary. citeturn7view0turn17view0turn8view4

Because results are increasingly scaffold- and protocol-sensitive, the highest-value contribution for your work is likely to be a **reusable representation-and-query story**, backed by causal analysis about which software layers matter for which issue types. citeturn9view5turn31view0turn31view1

The one sentence I would want reviewers to remember is this: **repository-level issue solving is bottlenecked by incomplete software representations, not only by weak patch generation; a ten-layer CKG plus a layer-aware query interface gives the agent the right evidence at the right granularity**. That thesis subsumes the main lessons of ARISE on granularity, SGAgent on planning, LIDL on semantic typing and validation, Prometheus on reproduction and end-to-end workflow, and KGCompass on multi-hop historical context. citeturn13view0turn11view0turn17view0turn20view0turn22view1
