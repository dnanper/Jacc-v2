Đúng. Tôi đề xuất triển khai thành một hệ tên tạm:

```text
CKG-Evolve
= Base Coding Agent
+ CKG primitive functions
+ Online tool synthesis
+ trajectory logging
+ offline rule/tool/policy promotion
+ benchmark-driven agent versioning
```

Về nguồn cảm hứng: **Live-SWE-agent** là pattern online self-evolution, tức agent mở rộng/sửa capability trong runtime khi giải issue; paper báo evaluate trên SWE-bench Verified và SWE-Bench Pro. **DGM** là pattern offline evolution: duy trì archive nhiều coding agents, để agent tự sửa code của chính nó, rồi validate bằng benchmark. **HGM** cải tiến DGM bằng cách chọn nhánh self-improvement theo “metaproductivity”, không chỉ theo score hiện tại. ([arXiv][1])

# 1. Mục tiêu thiết kế

Bạn không nên bắt đầu bằng “agent tự sửa toàn bộ hệ thống”. Nên bắt đầu bằng mục tiêu hẹp hơn:

```text
Agent được phép tự viết tool nhỏ để compose các hàm CKG,
dùng tool đó giải task hiện tại,
log lại,
sau nhiều task thì promote tool/rule tốt thành capability chính thức.
```

Mục tiêu cuối cùng:

```text
Base Agent v1
  ↓ run N benchmark tasks
Online tools được sinh ra trong từng task
  ↓ log + analyze
Offline evolution tạo candidate agents
  ↓ benchmark validation
Base Agent v2
  ↓ repeat
```

Không train LLM. Chỉ evolve:

```text
tool
workflow
prompt policy
retrieval strategy
context packing
graph-query strategy
verifier/ranker
agent scaffold code
```

# 3. Core design: chia thành 7 module

## Module 1 — CKG primitive library

Đây là lớp hàm nguyên thủy, không agentic.

Ví dụ API:

```python
class CKG:
    def search_symbols(self, query: str, top_k: int = 20) -> list[SymbolNode]: ...
    def get_definition(self, symbol: str) -> CodeSpan: ...
    def get_references(self, symbol: str) -> list[CodeSpan]: ...
    def get_callers(self, symbol: str, depth: int = 1) -> GraphSubtree: ...
    def get_callees(self, symbol: str, depth: int = 1) -> GraphSubtree: ...
    def find_tests_for_symbol(self, symbol: str) -> list[TestNode]: ...
    def trace_endpoint_flow(self, route: str) -> FlowGraph: ...
    def rank_related_nodes(
        self,
        query: str,
        seed_nodes: list[str],
        signals: list[str],
        top_k: int = 20,
    ) -> list[RankedNode]: ...
```

Ở giai đoạn đầu, chỉ cần 8–12 primitive thật chắc. Đừng làm quá nhiều tool sẵn. Online evolve cần có “nguyên liệu” tốt để tự compose.

## Module 2 — Base Agent

Base Agent không nên quá thông minh lúc đầu. Nên có workflow cố định vừa đủ:

```text
1. Understand issue
2. Choose localization strategy
3. Query CKG primitives
4. Decide whether to create temporary tool
5. Build context pack
6. Generate patch
7. Run tests
8. Revise
9. Submit
```

Pseudo-code:

```python
class BaseAgent:
    def solve(self, task: Task) -> SolveResult:
        state = AgentState(task=task)

        for step in range(self.max_steps):
            observation = self.observe(state)

            decision = self.policy.decide(
                task=task,
                state=state,
                available_ckg_functions=self.ckg_registry.describe(),
                available_tools=self.tool_registry.describe(),
            )

            if decision.type == "CALL_CKG":
                result = self.ckg_executor.call(decision.function, decision.args)

            elif decision.type == "CREATE_TOOL":
                tool = self.tool_designer.create_tool(decision.spec)
                result = self.tool_sandbox.run(tool, decision.args)

            elif decision.type == "EDIT_CODE":
                result = self.editor.apply_patch(decision.patch)

            elif decision.type == "RUN_TEST":
                result = self.test_runner.run(decision.test_command)

            elif decision.type == "SUBMIT":
                return self.submit(state)

            self.logger.record(decision, result)
            state.update(decision, result)

        return self.fail(state)
```

Điểm quan trọng: agent không gọi Python tùy tiện vào toàn bộ system. Nó chỉ được tạo tool trong sandbox và dùng CKG qua façade/SDK được kiểm soát.

## Module 3 — Online Tool Designer

Online evolve nằm ở module này.

Agent được phép tạo tool như:

```python
# generated_tools/task_0042/trace_discount_flow.py

from ckg_sdk import CKG

ckg = CKG.open()

route = "/checkout"
flow = ckg.trace_endpoint_flow(route)

candidates = ckg.rank_related_nodes(
    query="coupon loyalty points discount applied twice",
    seed_nodes=[n.id for n in flow.nodes],
    signals=["call_graph", "test_proximity", "symbol_name"],
    top_k=20,
)

for c in candidates:
    print(c.to_json())
```

Nhưng phải giới hạn:

```text
- read-only với CKG
- read-only với repo, trừ editor chính thức
- timeout
- max file size
- max output tokens
- no network
- no hidden benchmark access
- dependency whitelist
- tool code được lưu lại
```

Bạn nên có 2 mode:

```text
Mode A: Python script tool
  Linh hoạt, dễ implement.

Mode B: CKG Query DSL
  An toàn hơn, dễ analyze/promote hơn.
```

Tôi khuyên bắt đầu bằng Python script vì nhanh, sau đó ép dần về DSL.

Ví dụ DSL sau này:

```yaml
tool_name: endpoint_discount_localizer
inputs:
  route: "/checkout"
  issue_terms:
    - coupon
    - loyalty
    - discount
pipeline:
  - trace_endpoint_flow: { route: "$route" }
  - expand_callees: { depth: 2 }
  - rank_related_nodes:
      query: "$issue_terms"
      signals: ["semantic", "graph_distance", "test_proximity"]
  - attach_tests: {}
output:
  top_k: 15
```

DSL giúp offline analyzer dễ phát hiện pattern hơn so với đọc code Python arbitrary.

## Module 6 — Offline Evolution Engine

Offline evolve gồm 5 bước.

### Bước 1: Mine successful trajectories

Tìm các pattern trong task thành công:

```text
- tool nào được tạo?
- tool compose những CKG primitive nào?
- graph path nào xuất hiện?
- strategy nào giúp localization đúng?
- context pack nào ngắn nhưng đủ?
- test nào được chạy trước khi patch thành công?
```

### Bước 2: Contrast với failed trajectories

Không chỉ nhìn task thành công. Phải so với task fail:

```text
Successful tasks:
  trace_endpoint_flow → rank_related_nodes → attach_tests

Failed tasks:
  semantic_search only → too many files → wrong edit
```

### Bước 3: Propose reusable capability

Offline engine tạo proposal dạng structured:

```yaml
proposal_id: promote_endpoint_flow_localizer
type: official_tool
evidence:
  used_in_successful_tasks: 38
  used_in_failed_tasks: 7
  avg_file_hit_at_5_delta: +0.21
  avg_context_tokens_delta: -0.18
change:
  add_tool: trace_endpoint_impact()
  add_policy_rule:
    if issue mentions HTTP route/status/request/response: use trace_endpoint_impact before semantic_search
risk: may overfit web/API repos
validation_plan: run on endpoint-related validation split
  run on non-endpoint regression split
```

### Bước 4: Generate candidate agent versions

Không tạo một v2 duy nhất. Tạo nhiều candidate:

```text
v2.1 = add endpoint-flow official tool
v2.2 = add failing-test-first policy
v2.3 = add graph-distance ranker
v2.4 = combine v2.1 + v2.2
v2.5 = change context packer only
```

### Bước 5: Evaluate and promote

Chỉ promote nếu qua validation.

```text
Promote condition:
  resolved_rate improves
  localization improves
  cost does not explode
  non-target task regression acceptable
  no hidden-test leakage
```

DGM dùng ý tưởng “archive of generated agents” thay vì một chuỗi v1→v2 tuyến tính; đó là lý do bạn nên giữ nhiều candidate, lineage và score, không overwrite agent cũ. ([arXiv][2])

## Module 7 — Agent Archive

Lưu lại version tree:

```text
agent_v1
 ├── agent_v2_endpoint_flow
 ├── agent_v2_test_first
 │    └── agent_v3_test_first_context_packer
 └── agent_v2_graph_ranker
```

Metadata:

```json
{
  "agent_id": "v2_endpoint_flow",
  "parent_id": "v1",
  "changes": ["add trace_endpoint_impact tool", "add endpoint policy rule"],
  "scores": {
    "train_resolve_rate": 0.41,
    "valid_resolve_rate": 0.36,
    "file_hit_at_5": 0.72,
    "avg_cost_usd": 0.51
  },
  "regressions": ["config-related tasks slower"],
  "promoted": true
}
```

HGM gợi ý thêm một ý quan trọng: đừng chỉ chọn version có score hiện tại cao nhất; cần xem nhánh nào có khả năng sinh cải tiến tiếp theo tốt hơn. Ở MVP bạn chưa cần CMP đầy đủ, nhưng nên lưu lineage để sau này phân tích “dòng agent nào tiếp tục cải thiện”. ([arXiv][3])

# 5. Implementation plan theo giai đoạn

## Phase 0 — Build benchmark nhỏ trước

Trước khi evolve, cần benchmark nội bộ. Không có benchmark thì offline evolve vô nghĩa.

Tạo 30–50 task đầu tiên:

```text
10 bug localization tasks
10 small patch tasks
10 test-failure tasks
10 API/business-flow tasks
10 refactor/feature tasks nếu có
```

Mỗi task nên có:

```text
repo snapshot
issue text
expected changed files/functions nếu biết
test command
pass/fail oracle
ground-truth patch nếu có
```

Metric ban đầu:

```text
resolved_rate
file_hit@1 / @3 / @5
function_hit@5 / @10
context_tokens
cost
time
patch_files_changed
test_pass_rate
```

---

## Phase 1 — CKG primitives stable

Implement trước các primitive sau:

```text
search_symbols()
get_definition()
get_references()
get_callers()
get_callees()
find_tests_for_symbol()
rank_related_nodes()
build_context_pack()
```

Chưa cần CFG/DFG sâu. Cần graph ở mức symbol/function/file/test trước.

Exit criteria:

```text
- primitive API stable
- mỗi primitive có unit test
- output có node_id ổn định
- có ranking score explainable
- context pack build được từ node list
```

---

## Phase 2 — Base Agent v1 không online evolve

Mục tiêu là có baseline.

Workflow cố định:

```text
issue
 → semantic/symbol search
 → graph expansion depth 1
 → context pack
 → patch
 → run test
 → revise once
```

Không cho agent tự tạo tool vội.

Measure:

```text
Agent v1 baseline:
  resolved_rate
  localization_hit
  cost
  failure taxonomy
```

Exit criteria:

```text
- chạy được end-to-end trên 30–50 task
- log đầy đủ
- failure được phân loại
```

---

## Phase 3 — Add online evolve

Bật tool designer.

Ban đầu chỉ cho tạo tool read-only:

```text
Allowed:
  query CKG
  parse test output
  rank nodes
  summarize graph paths

Not allowed:
  edit repo directly
  modify CKG source
  network
  install packages
  read hidden tests
```

Tool tạo ra chỉ được output:

```text
candidate files
candidate symbols
graph paths
related tests
explanations
```

Patch vẫn qua official editor.

Exit criteria:

```text
Agent v1 + online evolve
  phải cải thiện localization hoặc context efficiency
  không làm cost/time tăng quá mức
  không tạo quá nhiều broken tools
```

---

## Phase 4 — Offline log mining

Sau khoảng K task, ví dụ K = 50 hoặc 100:

```text
collect trajectories
cluster generated tools
extract common CKG function sequences
compare success vs failure
produce proposals
```

Kết quả không phải code ngay, mà là proposal có evidence.

Ví dụ:

```yaml
proposal: add failing_test_first_localizer
evidence:
  success_delta_file_hit_at_5: +0.18
  avg_context_reduction: -22%
risk: only works when failing test is available
candidate_versions:
  - agent_v2_test_first_policy
  - agent_v2_test_first_tool
```

---

## Phase 5 — Candidate generation and validation

Tạo 3–5 candidate agent versions.

Chạy trên validation split chưa dùng để mine pattern.

```text
train split:
  dùng để mine logs

validation split:
  dùng để chọn candidate

held-out test split:
  chỉ dùng khi release agent version
```

Exit criteria để promote:

```text
resolved_rate + statistically meaningful
file_hit@5 tăng
context_tokens không tăng quá 20%
cost không tăng quá 30%
không giảm mạnh trên task type khác
```

---

## Phase 6 — Agent archive + repeated evolution

Khi có nhiều version:

```text
v1
v2_endpoint
v2_test_first
v2_graph_ranker
v3_combined
```

Lưu lineage, result, regression.

Sau này có thể dùng HGM-like selection:

```text
Không chỉ hỏi:
  agent nào score cao nhất?

Mà hỏi:
  nhánh agent nào tiếp tục sinh ra cải tiến tốt nhất?
```

# 6. Measurement design

Bạn cần đo 4 tầng.

## Tầng A — End-to-end task success

```text
resolved_rate
pass@1
patch_correctness nếu có human review
regression_test_pass_rate
```

Đây là metric cuối, nhưng không đủ.

---

## Tầng B — Localization quality

```text
file_hit@1
file_hit@3
file_hit@5
function_hit@5
function_hit@10
mean_rank_ground_truth_file
mean_rank_ground_truth_function
```

Nếu benchmark không có ground truth function, lấy từ gold patch:

```text
gold changed files = files trong reference patch
gold changed functions = functions overlapping reference diff
```

---

## Tầng C — CKG/tool quality

```text
ckg_calls_per_task
generated_tools_per_task
generated_tool_success_rate
generated_tool_runtime_error_rate
unique_ckg_function_compositions
graph_nodes_retrieved
irrelevant_context_ratio
context_tokens
context_precision
context_recall
```

Context precision/recall có thể tính gần đúng:

```text
context_recall =
  gold changed symbols present in context / all gold changed symbols

context_precision =
  gold relevant symbols in context / all symbols in context
```

---

## Tầng D — Offline evolution quality

```text
candidate_win_rate_vs_parent
validation_resolved_delta
heldout_resolved_delta
regression_count
cost_delta
tool_promotion_success_rate
policy_promotion_success_rate
```

Quan trọng nhất:

```text
Online evolve có giúp từng task không?
Offline evolve có tạo agent version tốt hơn trên task chưa thấy không?
```

# 7. Ablation bắt buộc

Để biết design có thật sự hoạt động, cần ít nhất 6 ablation:

```text
A0: Base Agent, no CKG
A1: Base Agent + raw CKG primitives
A2: Base Agent + fixed official tools
A3: Base Agent + online tool synthesis
A4: Base Agent + offline promoted tools
A5: Base Agent + online + offline evolve
```

Expected result hợp lý:

```text
A1 > A0 về localization
A2 > A1 về cost/stability
A3 > A2 trên task lạ/phức tạp
A4 > A2 trên benchmark tổng quát
A5 tốt nhất nhưng có thể cost cao hơn
```

Nếu A3 không hơn A2, nghĩa là online evolve đang tạo noise.

Nếu A4 không hơn A2, nghĩa là offline promotion đang overfit hoặc mine pattern sai.

# 8. Failure modes và cách xử lý

## Failure 1 — Online tools sinh ra nhiều nhưng không giúp

Dấu hiệu:

```text
generated_tools_per_task cao
tool_runtime_error_rate cao
resolved_rate không tăng
cost tăng
```

Nguyên nhân:

```text
agent không biết compose CKG primitives
primitive API khó dùng
tool output quá dài
tool không có objective rõ
```

Cách xử lý:

```text
- giảm quyền tool designer
- chuyển từ Python arbitrary sang DSL
- cung cấp tool templates
- bắt agent viết tool spec trước, code sau
- thêm reviewer kiểm tra tool trước khi chạy
- giới hạn max 1–2 generated tools/task
```

Fallback:

```text
Dùng fixed official tools thay vì online synthesis.
```

---

## Failure 2 — Agent dùng CKG nhưng localization vẫn sai

Dấu hiệu:

```text
file_hit@5 thấp
function_hit@10 thấp
context_recall thấp
```

Nguyên nhân:

```text
graph thiếu edge quan trọng
ranking yếu
semantic search kém
test-code link sai
issue cần runtime signal chứ graph tĩnh không đủ
```

Cách xử lý:

```text
- thêm test failure → code mapping
- thêm import/call/reference edge
- thêm endpoint/framework extractor
- thêm change history / git blame / recent edits
- dùng hybrid ranking: semantic + graph distance + test proximity
```

Fallback:

```text
Nếu CKG chưa đủ tốt, đừng để agent phụ thuộc hoàn toàn vào CKG.
Giữ semantic search + grep + file search như fallback.
```

---

## Failure 3 — Context pack quá to

Dấu hiệu:

```text
context_tokens tăng
LLM sửa sai file
irrelevant_context_ratio cao
```

Cách xử lý:

```text
- cap theo symbol, không theo file
- depth mặc định = 1
- chỉ expand call graph khi có seed symbol tốt
- thêm reranker
- đưa "excluded because..." để agent không mở rộng lại vùng sai
```

Fallback:

```text
Dùng Agentless-style localization:
  coarse file localization → fine function localization → repair.
```

---

## Failure 4 — Offline evolve overfit benchmark

Dấu hiệu:

```text
train score tăng
validation/test score không tăng
rule mới chỉ tốt trên một repo/task type
```

Cách xử lý:

```text
- tách train/validation/held-out nghiêm
- split theo repo, không chỉ theo task
- require improvement trên nhiều task families
- promote rule theo condition hẹp
- rollback nếu regression lớn
```

Fallback:

```text
Không promote vào Base Agent.
Giữ rule dưới dạng optional strategy được trigger có điều kiện.
```

---

## Failure 5 — Candidate v2 tốt hơn resolved_rate nhưng đắt hơn quá nhiều

Dấu hiệu:

```text
resolved +2%
cost +200%
runtime +300%
```

Cách xử lý:

```text
- dùng budget-aware policy
- chỉ bật online evolve cho task khó
- early stop nếu localization confidence cao
- cache CKG query
- reuse generated tool pattern
```

Metric promote nên là utility:

```text
utility =
  resolved_rate_gain
  - λ1 * cost_increase
  - λ2 * runtime_increase
  - λ3 * regression_rate
```

---

## Failure 6 — Agent tự tạo tool nguy hiểm hoặc khó kiểm soát

Dấu hiệu:

```text
tool đọc/ghi ngoài workspace
tool gọi network
tool modify repo bypass editor
tool output quá lớn
```

Cách xử lý:

```text
- sandbox container
- read-only mount cho repo
- generated tools chỉ được gọi ckg_sdk
- no network
- timeout
- output cap
- syscall/file access whitelist
```

Fallback:

```text
Chỉ cho tạo CKG DSL query, không cho tạo Python script.
```

---

## Failure 7 — Offline miner rút rule sai

Dấu hiệu:

```text
proposal nghe hợp lý nhưng validation fail
```

Nguyên nhân:

```text
correlation ≠ causation
tool xuất hiện trong task thành công nhưng không phải nguyên nhân thành công
```

Cách xử lý:

```text
- contrast success vs failure
- replay trajectory with and without tool
- ablation per promoted rule
- require validation lift
```

Fallback:

```text
Dùng human-in-the-loop approve proposal trong giai đoạn đầu.
```

---

## Failure 8 — LLM yếu không đủ khả năng tự thiết kế tool

Dấu hiệu:

```text
tool code lỗi cú pháp
tool gọi sai API
tool logic lan man
```

Cách xử lý:

```text
- cung cấp examples/templates
- tool spec schema bắt buộc
- compile/test generated tool trước khi dùng
- dùng smaller search space: DSL
- cho model mạnh hơn chỉ ở step tool-design
```

Fallback:

```text
Không online evolve.
Dùng library official tools + fixed policy.
```

# 9. Rule promotion pipeline

Một online tool chỉ được promote nếu qua 5 cổng:

```text
Gate 1: Frequency
  Pattern xuất hiện đủ nhiều.

Gate 2: Association
  Pattern correlate với success/localization improvement.

Gate 3: Counterfactual
  Replay/ablation cho thấy bỏ pattern thì kém hơn.

Gate 4: Validation
  Candidate agent cải thiện trên validation split.

Gate 5: Regression
  Không làm hỏng task type khác quá mức.
```

Ví dụ promote:

```text
Generated tool pattern:
  trace_endpoint_flow
  → expand service callees depth 1
  → attach tests
  → rank by issue terms

Promoted official tool:
  trace_endpoint_impact(route, issue_terms)

Promoted policy:
  If issue has HTTP/API/route/status terms:
      call trace_endpoint_impact first
```

# 12. Khi design này không hoạt động thì làm gì?

Tôi sẽ chia thành 3 kịch bản.

## Kịch bản A — CKG không giúp localization

Kết luận:

```text
Vấn đề nằm ở graph/schema/ranking, không phải evolve.
```

Làm:

```text
- dừng online/offline evolve
- tập trung cải thiện CKG extraction
- thêm symbol resolution, test links, framework links
- benchmark riêng localization trước
```

Chỉ tiếp tục agent khi:

```text
CKG retrieval đánh bại grep/semantic baseline trên file_hit@k.
```

---

## Kịch bản B — CKG tốt nhưng online evolve không giúp

Kết luận:

```text
Agent không cần tự tạo tool; official tools đủ tốt hơn.
```

Làm:

```text
- tắt Python tool synthesis
- dùng fixed workflow + official CKG tools
- cho offline evolve chỉ optimize policy/context pack
```

Architecture fallback:

```text
Base Agent
  → official CKG tools
  → fixed localization
  → patch
  → verifier
```

Đây vẫn là hướng tốt; không nhất thiết phải self-evolve để có system mạnh.

---

## Kịch bản C — Online tốt nhưng offline không tạo v2 tốt hơn

Kết luận:

```text
Mining/promotion yếu hoặc benchmark quá nhỏ.
```

Làm:

```text
- tăng số task
- split theo repo/task type
- thêm human review proposal
- promote từng rule nhỏ thay vì combine nhiều thay đổi
- dùng ablation chặt hơn
```

Fallback:

```text
Giữ online evolve runtime-only.
Không promote thành base agent cho đến khi có evidence.
```

---

# 13. Design tôi khuyên dùng ngay

Bản an toàn nhất:

```text
Base Agent v1:
  fixed workflow

CKG:
  strong primitives

Online evolve:
  enabled only for localization/query tools
  no code editing from generated tools

Offline evolve:
  semi-automatic
  agent proposes rules/tools
  human approves initially
  benchmark validates before promotion
```

Tức là:

```text
Không để agent tự sửa core CKG ngay từ đầu.
Không để generated tool tự patch repo.
Không promote rule nếu chưa qua validation.
Không dùng resolved_rate đơn độc để đánh giá.
```

# 14. Final blueprint

```text
Stage 1:
  Build CKG primitives + fixed agent baseline.

Stage 2:
  Let agent create temporary CKG-query tools per task.

Stage 3:
  Log everything:
    CKG calls, generated tools, graph paths, context, edits, tests.

Stage 4:
  Mine logs:
    successful tool patterns vs failed patterns.

Stage 5:
  Promote:
    repeated useful generated tools → official tools.
    repeated useful action sequences → policy rules.
    repeated useful context layouts → context packer changes.

Stage 6:
  Generate multiple candidate agents:
    v2.1, v2.2, v2.3...

Stage 7:
  Validate:
    end-to-end success
    localization
    cost
    regression

Stage 8:
  Archive:
    keep lineage, scores, failures.

Stage 9:
  Repeat.
```

Câu chốt: **online evolve biến CKG primitives thành task-specific query programs; offline evolve biến những query programs thành agent capability lâu dài.**
